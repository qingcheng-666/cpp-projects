## 一、先搞懂：为什么需要跳表？

### 1.1 从"找东西"说起

假设你有一堆**有序**的数字：`3, 6, 7, 9, 12, 17, 19, 21, 25, 26`，现在要查 `19` 在不在。

**方案 A：有序数组**
可以用二分查找，每次砍一半，`O(log n)`。很快。
但**插入/删除很慢**——往中间插一个数，后面所有元素都要往后挪，`O(n)`。

**方案 B：链表**
插入/删除很快，改几个指针就行，`O(1)`（前提是你已经找到了位置）。
但**查找很慢**——只能从头一个一个走，`O(n)`。

看出来了吗？**数组擅长查，链表擅长改，各有短板。**

### 1.2 跳表的核心思路：给链表加"索引"

既然链表查找慢是因为"只能一步一步走"，那能不能**建一条"快速通道"**，一次跳过好几个节点？

比如在上面的链表之上，再建一条链表，只连接**部分**节点：

```
L1:  H ──────────────────> 7 ──────────> 19 ──────> 25
                            │             │          │
L0:  H ──> 3 ──> 6 ──> 7 ──> 9 ──> 12 ──> 17 ──> 19 ──> 21 ──> 25 ──> 26
```

现在查 `19`：
- 先在 L1 走：`H → 7 → 19`，2 步就到了
- 如果走 L0 要 7 步

**这就是"空间换时间"**：多花一条链表的空间，换来更快的查找。

### 1.3 那就多建几层

一层索引能快一点，那建多层呢？

```
L3:  H ──────────────────────────────────────> 19
L2:  H ──────────> 7 ────────────────────────> 19 ──────────> 25
L1:  H ──> 3 ──> 6 ──> 7 ──> 9 ──> 12 ──> 17 ──> 19 ──> 21 ──> 25 ──> 26
L0:  H ──> 3 ──> 6 ──> 7 ──> 9 ──> 12 ──> 17 ──> 19 ──> 21 ──> 25 ──> 26
```

查 `19`：`L3` 直接 `H → 19`，**1 步**。

层数越高，节点越少、跳得越远。查找时**从最高层开始，能往右就往右，不能就往下一层**——这就是跳表的全部精髓。

> 打个比方：**高铁（高层，站少）→ 普快（中层）→ 公交（底层，每站都停）**。
> 你要去某个小站，先坐高铁到大城市，再换普快，最后换公交。

## 二、关键问题：谁该出现在高层？

如果高层只放"重要的"节点，那就得**动态维护平衡**（像红黑树那样旋转），实现会变得很复杂。

跳表的天才之处在于：**不维护，直接掷硬币！**

每插入一个新节点，就**掷硬币**决定它有多高：

```
第 1 次掷硬币：正面 → 再升一层
第 2 次掷硬币：正面 → 再升一层
...一直掷到反面，或到达最高层上限
```

具体规则（原项目的写法）：

```cpp
int k = 1;
while (rand() % 2) { k++; }        // 每次 1/2 概率继续升层
k = (k < _max_level) ? k : _max_level;   // 封顶
return k;
```

算一下概率：

| 层高 | 概率 | 100 万个节点里大约有几个 |
|---|---|---|
| ≥ 1 | 1/2 | 500,000 |
| ≥ 2 | 1/4 | 250,000 |
| ≥ 3 | 1/8 | 125,000 |
| ≥ 10 | 1/512 | ~2,000 |
| ≥ 18 | 1/131072 | ~8 |

**期望层高 = 1 + 1/2 + 1/4 + 1/8 + ... = 2**

也就是说：**平均每个节点只多花 1 个指针**（加上 level 0 那个共 2 个），就能得到 `O(log n)` 的查找。这就是跳表"性价比"极高的原因。

而且因为是随机的，**不需要任何旋转/再平衡**，代码简单得多——这正是 Redis、LevelDB 选跳表而不是红黑树的核心原因之一。

## 三、亲手跑一遍（重要）

别光看，跑一下这个程序，你能**直接看到跳表长什么样**：

```bash
cd ~/Skiplist-CPP
g++ learn/skiplist_visual.cpp -o bin/visual --std=c++11
./bin/visual
```

你会看到类似这样的输出：

```
  L4 ┆ H   (空，还没用到)
  L3 │ H ------>3 --------------------------------------------------->19
  L2 │ H ------>3 --------------->7 --------------------------------->19 -------------->25
  L1 │ H ------>3 ------>6 ------>7 ------>9 ------>12 ----->17 ----->19 ----->21 ----->25 ----->26
  L0 │ H ------>3 ------>6 ------>7 ------>9 ------>12 ----->17 ----->19 ----->21 ----->25 ----->26
       ^
       H = 头节点(不存数据)   L0 = 最底层(存全部数据)
```

**怎么看这张图：**
- **竖着看是一层**，`L0` 在最下面，`L4` 在最上面
- **横着看是一条链表**，`H` 是头节点（不存数据，只是个入口）
- **上下对齐**：同一个 key 在不同层的列位置是一样的，所以能直接看出"跳跃"
- `L0` 有全部 10 个节点；`L3` 只有 `3` 和 `19` 两个 —— **高层稀疏，这就是索引**

程序还会打印**查找过程的每一步**，你能看到"在哪一层停、为什么往下走"：

```
查找 19：
  L3: -1 → 3   (3 < 19，继续右移)
  L3: 停在 3（右边是 19 ≥ 19，下一层）
  L2: 3 → 7    (7 < 19，继续右移)
  ...
  ✅ 找到 19
```

**建议你改一改程序里的数据再跑**，比如把 `data[]` 换成你自己的数字，或者把 `MAX_LEVEL` 改成 2 或 6，看看结构怎么变。**动手改比看十遍文档都管用。**

## 四、三个必须记住的结论

1. **跳表 = 有序链表 + 多级索引**。高层稀疏跳得远，底层密集走得细。
2. **层高靠掷硬币，不靠平衡**。期望层高 2，空间代价极小，代码极简。
3. **查找 = 从最高层往下，每层尽量右移**。期望 `O(log n)`。

| 操作 | 期望复杂度 |
|---|---|
| 查找 | O(log n) |
| 插入 | O(log n) |
| 删除 | O(log n) |
| 空间 | O(n) |

## 五、面试常问：跳表 vs 红黑树 vs 哈希表

| | 跳表 | 红黑树 | 哈希表 |
|---|---|---|---|
| 查找 | O(log n) | O(log n) | **O(1)** |
| **范围查询** | ✅ 天然支持 | ✅ 支持（中序遍历） | ❌ 不支持 |
| 实现难度 | **简单** | 复杂（旋转/变色） | 中等 |
| 并发友好度 | **好**（可局部加锁） | 差（旋转影响面大） | 中等（扩容麻烦） |
| 最坏情况 | O(n)（概率极低） | **稳定 O(log n)** | O(n)（全冲突） |

**为什么 Redis 的 ZSET、LevelDB/RocksDB 的 MemTable 都用跳表？**
- 需要**范围查询**（ZSET 的 `ZRANGE`、LevelDB 的有序刷盘）→ 排除哈希表
- 需要**实现简单 + 并发友好** → 优于红黑树
- 最坏 O(n) 的概率极低（要连续掷出 log n 次正面），工程上可接受

> 你原项目的 README 说"redis、leveldb、rocksdb 的核心存储引擎就是跳表"——**这句话基本对**，
> 准确说是：Redis 的**有序集合 ZSET** 用了跳表；LevelDB/RocksDB 的**内存表 MemTable** 用了跳表。
> 说"核心存储引擎"稍微夸张了点，面试时说得准确些更好。
