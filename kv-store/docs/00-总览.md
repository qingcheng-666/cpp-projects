> 基于 [代码随想录 Skiplist-CPP](https://github.com/youngyangyang04/Skiplist-CPP)（GPL-3.0）
> 原版 **268 行**有效代码 → 本项目 **1384 行**，**351 项测试全过**

---

## 这个仓库是什么

**一个从 268 行教学代码长出来的、可用的 KV 存储引擎。**

原版是个跳表教学项目：9 个文件、约 400 行、没有测试、没有持久化保证、有 7 个真实缺陷。

本项目做了三件事：

1. **读懂它** —— 跳表入门 + 逐行源码导读（`learn/`）
2. **修好它** —— 定位并修复 7 个缺陷，用最小改动（有效代码只增 7 行）
3. **长出它** —— 补上范围查询、WAL 崩溃恢复、网络层，从"数据结构练习"变成"存储引擎"

**最终形态**：一个支持任意字符串 key、带崩溃恢复、能用 `redis-cli` 直连的 KV 服务。

## 30 秒上手

```bash
cd ~/Skiplist-CPP/fixed

# 编译
make server

# 启动服务（默认 6380 端口，数据在 /tmp/kvdata）
./bin/kv_server 6380 /tmp/kvdata
```

另开一个终端：

```bash
redis-cli -p 6380 ping                          # PONG
redis-cli -p 6380 set user:1001:name alice      # OK
redis-cli -p 6380 get user:1001:name            # alice
redis-cli -p 6380 set 中文键 中文值              # OK（UTF-8 key）
redis-cli -p 6380 scan user: "user:$(printf '\xff')"   # 前缀范围查询
redis-cli -p 6380 snapshot                      # 快照压缩 WAL
redis-cli -p 6380 info                          # 服务状态
```

**崩溃恢复演示**（最有说服力的部分）：

```bash
make crash      # 3 轮 kill -9，验证所有已确认写入全部恢复
make compare    # 对照：原版恢复 0 条，WAL 版恢复 5000 条
```

## 改造历程

每一阶段都有独立的代码、测试和文档。

### P1 · 修复 7 个真实缺陷

原版有 7 个缺陷，**全部实测复现**（不是看代码猜的）：

| # | 缺陷 | 原版实测 | 修复 |
|---|---|---|---|
| 1 | 递归析构爆栈 | 100 万节点 `exit=139` 段错误 | 改迭代，栈深度 O(1) |
| 2 | 头文件定义全局变量 | 多 TU 链接 `multiple definition` | 锁改成员变量、分隔符改类内常量 |
| 3 | `search` 无锁 | TSan 报 data race | `shared_mutex` 读写锁 + RAII |
| 4 | `dump_file` 静默丢数据 | 目录不存在时 `exit=0` 无报错 | 返回 `bool` + 检查 `is_open()` |
| 5 | 层高从 1 开始，L1 冗余 | L1 占比 100%（与 L0 全同） | 从 0 开始，L1 占比 50% |
| 6 | 无 update 语义 | `set_value()` 是死代码 | 新增 `upsert_element`（P4 需要） |
| 7 | 头节点未初始化 | `-Wall` 告警 | `K k{}` 值初始化 |

**有效代码只增加 7 行** —— 是精准小改动，不是重写。

📄 `docs/03-P1修复对照.md` ｜ `fixed/P1.diff` ｜ `make test`

### P2 · Key Codec：让 key 支持任意字符串

原来 `SET username alice` 直接报错（key 只能是 int）。

**关键洞察**：跳表本身就是 `template<typename K, typename V>`，比较用 `operator<`，int 走数值比较、string 走字典序 —— **天然都对，一行不用改**。真正卡住的只有**序列化**。

- 抽出 `KeyCodec<K>` 策略（int / string 两套实现）
- **修了一个真 bug**：原版用 `find`（第一个冒号）切分，含冒号的 key 被截断 → 改 `rfind`
- **快照格式从文本行改成长度前缀二进制** —— 因为 string key 里含 `\t` 或 `\n` 会破坏文本行格式

📄 `docs/07-P2-KeyCodec.md` ｜ `make p2` / `make p2e2e`

### P3 · 迭代器 + 范围查询

原版只有 `display_list()` 能打印，**等于把跳表最大的卖点浪费了** —— 范围查询恰恰是跳表相对哈希表唯一不可替代的优势（Redis ZSET 用它就是为了 `ZRANGE`）。

新增：`begin/end`、`lower_bound`、`scan`、`scan_n`、`count_range`、`seek`。

**性能实测**（100 万数据，取 100 条 × 1000 次）：

| 方式 | 单次 | 倍数 |
|---|---|---|
| **跳表 `scan()`** | 25.8 µs | **1.00x** |
| `std::map` `lower_bound` | 25.9 µs | 1.00x |
| 哈希表全量扫描 | 108 ms | **4193x** |

跳表和 `std::map` 打平是**符合预期**的（都是 O(log n) 定位）；**哈希表慢 4193 倍才是重点** —— 它无序，范围查询只能全量扫。

📄 `docs/04-P3范围查询.md` ｜ `make p3` / `make bench`

### P4 · WAL 预写日志与崩溃恢复

**这是"玩具"和"存储引擎"的分界线。**

原版只有 `dump_file()`：手动调用、全量覆盖、**没有任何崩溃恢复能力**。

新增：`crc32 + op + klen + vlen + key + value` 的 WAL 记录格式，先写日志落盘再改内存。

**kill -9 实测**（3 轮，每轮随机时刻强杀）：

```
第 1 轮  ACK 4096 条 → 恢复 4096 条  missing=0 wrong=0
第 2 轮  ACK 4116 条 → 恢复 4116 条  missing=0 wrong=0
第 3 轮  ACK 1991 条 → 恢复 1991 条  missing=0 wrong=0
```

**对照实验**（同样场景写 5000 条后 kill -9）：

| | 原版 | WAL 版 |
|---|---|---|
| 崩溃后恢复 | **0 条** | **5000 条** |
| 丢失 | **5000 条** | **0 条** |

📄 `docs/05-P4-WAL崩溃恢复.md` ｜ `make p4` / `make crash` / `make compare`

### P6 · 网络层：RESP 协议

**实现了 RESP 协议子集，`redis-cli` 可以直接连。**

核心难点：**TCP 是字节流、没有消息边界** —— 一次 `read` 可能拿到半条命令、一条半、或正好 N 条。实现了增量式状态机解析器。

**调试中踩的 4 个真实坑**（都记在文档里）：
1. `redis-cli` 发的命令名是**小写**的 → 所有命令 unknown
2. `--pipe` 模式会在命令后发一个**空行** → 被当成协议错误
3. 结束时发 `ECHO <magic>` 做同步校验 → 不实现就永远报错
4. `redis-benchmark` 启动时探测 `CONFIG` → 不实现会告警

**性能对照实验**：初测只有 800 QPS，觉得低，就启动原生 `redis-server` 用同样命令测 —— **它也只有 832 QPS，单客户端延迟我的还略低**。所以瓶颈在虚拟机网络栈，不在代码。

📄 `docs/06-P6网络层RESP.md` ｜ `make p6` / `make p6bench` / `make run`

### P5 · backward 指针

P3 的反向遍历是 O(range)（因为原版只有 forward 指针），我在文档里主动标注了这个局限。

P5 给 level 0 加 `backward` 指针（**和 Redis 的 `zskiplistNode` 一致**），变成真正的 O(log n + n)。

**复杂度实测**（100 万数据，各取 100 条）：

| 取数位置 | 耗时 |
|---|---|
| 表尾 | 0.066 ms |
| 表头 | 0.060 ms |

**几乎相同 —— 证明不再依赖 `start_key` 的位置。** P3 的旧实现在表尾要先扫 100 万次。

📄 `docs/08-P5-backward指针.md` ｜ `make p5`

## 这个项目能讲什么

**面试时按这个顺序讲，每一句都有实测证据：**

1. **数据结构选型** —— 为什么 KV 引擎用跳表而不是红黑树/哈希表？范围查询 + 并发友好 + 实现简单，Redis ZSET 同款。

2. **发现并修复 7 个缺陷** —— 这是最强的加分项。不是"我实现了跳表"，而是"我在这 268 行里找出了 7 个真实缺陷，每个都实测复现，修复只增加了 7 行有效代码"。

3. **从数据结构到存储引擎** —— 加 WAL 实现崩溃恢复，能现场演示 `kill -9` 后数据不丢（missing=0 wrong=0），并有原版对照（恢复 0 条）。

4. **范围查询的量化优势** —— 25.8 µs vs 哈希表 108 ms，**4193 倍**。有数字、有对比、有结论。

5. **工程判断力** ——
   - 反向遍历原版做不到 O(log n)，我先标注局限（P3），再加 backward 指针解决（P5）
   - 测出 800 QPS 觉得低，就启动原生 Redis 对照，确认瓶颈在 VM 网络栈而非代码
   - 快照格式从可读文本改成二进制，因为 string key 会破坏文本格式 —— **选了正确性**

6. **并发正确性** —— P6 做多线程时用 TSan 发现 P4 的 WAL 写路径有数据竞争，修复分两层（WAL 加锁 + store 级锁保证日志顺序与内存顺序一致）。

## 一个诚实的边界说明

**这个 KV 引擎适合做什么、不适合做什么：**

✅ **适合**：会话状态缓存、配置存储、有序数据集的范围查询、需要崩溃恢复的轻量 KV

❌ **不适合**：存聊天消息历史（没有二级索引、没有事务、没有 TTL、单机无分片）

**知道自己的项目不适合什么，比声称"什么都能做"更有说服力。** 面试官最怕听到"我什么都能做"，最喜欢听到"这里不适合用它，因为……"。
