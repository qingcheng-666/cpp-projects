## 修复 1：递归析构 → 迭代析构

### 原版（`skiplist.h` 约 400 行）

```cpp
if(_header->forward[0]!=nullptr){
    clear(_header->forward[0]);
}
delete(_header);

// 而 clear 是：
void SkipList<K, V>::clear(Node<K, V> * cur)
{
    if(cur->forward[0]!=nullptr){
        clear(cur->forward[0]);     // ← 递归
    }
    delete(cur);
}
```

### 问题

递归深度 = **节点总数**。100 万节点 × 每帧约 48 字节 ≈ **48MB**，而 Linux 默认栈只有 **8MB** → 栈溢出 → 段错误。

### 修复

```cpp
clear(_header->forward[0]);   // 内部已能处理 nullptr

void SkipList<K, V>::clear(Node<K, V> * cur)
{
    while (cur != nullptr) {
        Node<K, V>* next = cur->forward[0];   // 先记住后继
        delete cur;                           // 再删当前
        cur = next;
    }
}
```

**为什么先存后继再删？** 因为 `delete cur` 之后 `cur->forward[0]` 就是野指针了，读它会崩溃。

**栈深度从 O(n) 降到 O(1)。**

### 验证

```bash
# 原版：段错误
./bin/p1_dtor_orig ; echo $?    # 139

# 修复版：正常
./bin/p1_dtor_fixed ; echo $?   # 0
```

## 修复 2：头文件全局变量 → 成员变量

### 原版（文件开头，全局作用域）

```cpp
std::mutex mtx;                    // ← 这是「定义」，不是「声明」
std::string delimiter = ":";
```

### 问题

头文件被**多个 `.cpp`** include 时，每个翻译单元都生成一份定义，链接时冲突：

```
/usr/bin/ld: multiple definition of `mtx'; first defined here
/usr/bin/ld: multiple definition of `delimiter[abi:cxx11]'; first defined here
collect2: error: ld returned 1 exit status
```

**这直接堵死了多文件工程化**——你想拆成 `kv_server.cpp` + `main.cpp` 就编不过。而"加上网络层"（P6）的第一步就是拆文件。

### 修复

```cpp
class SkipList {
    // ...
private:
    std::shared_mutex _rwlock;                      // 锁变成成员变量
    static constexpr char kDelimiter = ':';         // 分隔符变成类内常量
};
```

**顺带解决的第二个问题**：原来那一把 `mtx` 是**全局**的，所有 `SkipList` 实例**共享同一把锁**，不同实例之间也会互相阻塞。改成成员变量后，每个实例有自己的锁。

### 三种改法对比（面试可能问）

| 改法 | 说明 | 适用 |
|---|---|---|
| `inline`（C++17） | `inline std::mutex mtx;` | 最省事，但仍是全局锁 |
| 移到 `.cpp` + `extern` | 头文件只留声明 | 传统做法，但 `skiplist.h` 是 header-only，没有 `.cpp` |
| **改成成员变量** ✅ | 我用的这个 | 最好：既解决链接冲突，又解决锁粒度过粗 |

## 修复 3：`search` 无锁 → `shared_mutex` 读写锁

### 原版

```cpp
std::mutex mtx;              // 全局互斥锁

int  insert_element(...) { mtx.lock(); ... mtx.unlock(); }   // 加锁
void delete_element(...) { mtx.lock(); ... mtx.unlock(); }   // 加锁
bool search_element(...) { /* 完全不加锁！ */ }               // ← 没锁
void display_list()      { /* 完全不加锁！ */ }
int  size()              { /* 完全不加锁！ */ }
```

### 问题

**这是一个"写写互斥"的容器，不是"读写安全"的容器。**

一个线程 `insert`（改 `forward` 指针）的同时，另一个线程 `search`（读 `forward` 指针）→ **数据竞争**。

实测（ThreadSanitizer）：
```
WARNING: ThreadSanitizer: data race
  Read of size 8 at ... by thread T2:
    #0 SkipList<int, std::string>::search_element(int)
```

**后果**：读线程可能读到正在被改写的指针，轻则查错、重则**解引用野指针崩溃**。

### 修复

```cpp
#include <mutex>          // unique_lock 在这里
#include <shared_mutex>   // shared_mutex / shared_lock 在这里

std::shared_mutex _rwlock;      // 成员变量

// 写操作：独占锁
int insert_element(...) {
    std::unique_lock<std::shared_mutex> lock(_rwlock);
    ...
}

// 读操作：共享锁（多个读可以并发）
bool search_element(...) {
    std::shared_lock<std::shared_mutex> lock(_rwlock);
    ...
}
```

### 为什么用 `shared_mutex` 而不是 `mutex`？

跳表是**读多写少**的典型场景。用普通 `mutex` 的话，100 个读线程也要排队；用 `shared_mutex`，**多个读可以同时进行**，只有写才独占。

### 顺手修掉的 RAII 问题

原版是**手写加解锁**，而且 `insert_element` 里有**两条 return 路径**：

```cpp
if (current != NULL && current->get_key() == key) {
    std::cout << "key: " << key << ", exists" << std::endl;
    mtx.unlock();          // ← 手写了一次
    return 1;
}
// ...
mtx.unlock();              // ← 又手写了一次
return 0;
```

**这种写法很容易漏**：以后加一条新的 `return` 分支，忘了写 `unlock()` 就是**死锁**。

改成 `std::unique_lock` 后**自动解锁**（RAII），两条 return 都不用管了。

### ⚠️ 改造时最容易踩的坑

`load_file()` 内部调用 `insert_element()`，而 `insert_element` **自己会加写锁**。

如果给 `load_file()` 也加锁，就是**同一线程重复获取非递归锁 → 死锁**。

```cpp
void load_file() {
    // 这里【不能】加锁！因为 insert_element 内部会加锁
    _file_reader.open(STORE_FILE);
    while (getline(_file_reader, line)) {
        insert_element(stoi(*key), *value);   // ← 它自己加锁
    }
}
```

我在代码里加了注释提醒。**规范做法**是把逻辑拆成 `_nolock` 私有版本，公开接口加锁后调用它。这一步留给 P2 做。

### 验证

```bash
# 原版：TSan 报 3 处 data race
# 修复版：TSan 无告警
```

> 注意：这台 VM 上 TSan 需要关 ASLR 才能跑：`setarch $(uname -m) -R ./程序`

## 修复 4：`dump_file` 静默丢数据

### 原版

```cpp
void SkipList<K, V>::dump_file() {          // ← 返回 void
    _file_writer.open(STORE_FILE);
    // ← 从不检查 is_open()！
    Node<K, V> *node = this->_header->forward[0]; 
    while (node != NULL) {
        _file_writer << ... ;
        node = node->forward[0];
    }
    _file_writer.flush();
    _file_writer.close();
    return ;
}
```

### 问题

`store/` 目录不存在时（比如在别的目录运行程序），`open()` **失败**，但代码**照样往下走、照样打印成功**，最后返回 `void`、**进程退出码 0**。

**数据一条都没写，调用方却以为落盘成功了。** 这是生产环境最危险的"静默数据丢失"。

### 修复

```cpp
bool SkipList<K, V>::dump_file() {          // ← 改成返回 bool
    std::unique_lock<std::shared_mutex> lock(_rwlock);
    _file_writer.open(STORE_FILE);

    if (!_file_writer.is_open()) {          // ← 检查！
        std::cerr << "[dump_file] 无法打开文件: " << STORE_FILE << std::endl;
        return false;
    }
    // ...
    _file_writer.flush();
    bool ok = _file_writer.good();          // ← 写过程中出错也要能发现
    _file_writer.close();
    return ok;
}
```

**两个检查缺一不可**：
- `is_open()` 捕获"打不开"（目录不存在、权限不足）
- `good()` 捕获"打开了但写失败"（磁盘满）

### 为什么用 `unique_lock` 而不是 `shared_lock`？

因为 `dump_file` 会**改写成员 `_file_writer`**，两个并发 dump 会互相踩。而 `search` 只读跳表结构，可以用共享锁。

**判断标准：这个操作会不会改成员状态。**

### 验证

```bash
cd /tmp && rm -rf store
# 原版：exit=0，store/ 没创建，无报错
# 修复版：exit=1，打印错误
```

## 修复 5：层高从 1 开始 → 从 0 开始

### 原版

```cpp
int SkipList<K, V>::get_random_level(){
    int k = 1;                    // ← 从 1 开始
    while (rand() % 2) { k++; }
    k = (k < _max_level) ? k : _max_level;
    return k;
}
```

### 问题

`k` 从 **1** 开始，意味着**每个节点的最小层高是 1**，也就是**至少有 2 层**（`forward` 数组长度 = `level+1` = 2）。

后果：**L1 必然包含全部节点，和 L0 完全一样**——白白浪费一个指针，起不到任何"索引/跳跃"作用。

实测（10 万次抽样）：

| | 最小层高 | L1 占比 |
|---|---|---|
| 原版 | **1** | **100%** ← L1 == L0 |
| 修复版 | **0** | **50.0%** ← L1 真正稀疏 |

可视化输出也能直接看到：
```
L1 │ H ------>3 ------>6 ------>7 ------>9 ...   ← 和 L0 一模一样
L0 │ H ------>3 ------>6 ------>7 ------>9 ...
```

### 修复

```cpp
int k = 0;      // ← 从 0 开始
while (rand() % 2) { k++; }
```

这样 `P(level = 0) = 1/2`，只有一半节点出现在 L1 以上，**每一层才真正起到稀疏索引的作用**。

**空间收益**：平均指针数从 **3** 降到 **2**（期望层高从 3 降到 2）。

### 这个缺陷怎么发现的

这个不是跑测试跑出来的，是**读代码时看出来的**——`int k = 1` 和经典跳表写法 `int k = 0` 不一样。

**面试价值最高**：说明你不是背代码，而是真的理解了跳表的概率模型。

## 修复 6：VLA → `std::vector`

### 原版

```cpp
Node<K, V> *update[_max_level+1];                          // ← 变长数组
memset(update, 0, sizeof(Node<K, V>*)*(_max_level+1));  
```

### 问题

**VLA（变长数组）不是标准 C++**，是 GCC/Clang 的扩展，**MSVC 不支持**。想跨平台就编不过。

另外 `_max_level` 很大时（比如 32），栈上开销也不小。

### 修复

```cpp
std::vector<Node<K, V>*> update(_max_level + 1, nullptr);
```

一行搞定，自动初始化、自动释放，且完全标准。

> 注意 `insert_element` 和 `delete_element` **两处**都要改。

## 修复 7：头节点未初始化

### 原版

```cpp
K k;      // ← 对于 int，这是「未初始化」
V v;
this->_header = new Node<K, V>(k, v, _max_level);
```

### 问题

头节点的 `key`/`value` 虽然**从不参与比较**，但复制一个未初始化的 `int` 是**未定义行为**。

`-Wall` 下会报：
```
warning: 'k' may be used uninitialized [-Wmaybe-uninitialized]
```

### 修复

```cpp
K k{};    // ← 值初始化：int 变 0，std::string 变空串
V v{};
```

编译零告警。**这是"代码洁癖"级别的修复，但面试时提到能体现严谨。**

## 面试怎么讲 P1

不要说"我修了 7 个 bug"，按这个结构讲：

> "这个开源项目有 7 个缺陷，我用最小改动修掉了，**有效代码只增加了 7 行**。
>
> 最严重的是三个：
> - **递归析构**——`clear()` 沿链表递归，深度等于节点数，100 万节点爆栈。我改成迭代，栈深度降到 O(1)。
> - **`search` 无锁**——`insert`/`delete` 加了锁但 `search` 没加，是典型的数据竞争。我用 TSan 跑出了报告，然后换成 `shared_mutex` 读写锁，读操作可以并发。
> - **`dump_file` 静默失败**——从不检查 `is_open()`，目录不存在时数据一条没写却返回成功、退出码 0。我改成返回 `bool` 并检查 `is_open()` 和 `good()`。
>
> 还有一个是读代码时发现的：`get_random_level()` 里 `k` 从 1 开始，导致 L1 必然包含全部节点，和 L0 完全一样，白白浪费一个指针。经典跳表是从 0 开始的。"

**这个回答的杀伤力在于：每一句都有实测证据，而且最后一条证明你真的懂跳表。**
