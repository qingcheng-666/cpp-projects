## 一、为什么 P4 是分界线

**P4 之前，这是个"数据结构练习"；P4 之后，它才是"存储引擎"。**

原版的持久化只有一个 `dump_file()`：

| 问题 | 说明 |
|---|---|
| 需要**手动调用** | 不调用就永远不落盘 |
| **全量覆盖** | 每次把整个内存重写一遍，O(n) |
| **没有崩溃恢复** | 进程被 kill，上次 dump 之后的所有写入**全丢** |
| **没有校验** | 文件写坏了也不知道 |
| 不是 WAL | 没有增量、没有 fsync、没有恢复机制 |

**这一条最关键**：原版根本**没有"已确认的写入不会丢"这个保证**。

---

## 二、WAL 的核心思想

```
写路径：  写请求 → ① 追加 WAL（含 CRC + fsync）→ ② 改内存跳表 → ③ 返回成功
恢复：    启动时 → ① 加载快照 → ② 重放 WAL → 重建跳表
压缩：    WAL 超过阈值 → 全量快照 → 清空 WAL
```

### 顺序绝对不能反

**必须先写日志成功，再改内存。**

如果反过来（先改内存、再写日志），那么在"内存改完、日志还没落盘"之间崩溃，恢复时这条写入就丢了 —— 而**调用方可能已经收到了成功响应**。

这就是 WAL 名字的由来：**Write-Ahead**（日志先行）。

## 三、WAL 记录格式

```
+--------+--------+--------+--------+---------+---------+
| crc32  | op(1B) | klen   | vlen   |  key    |  value  |
|  4B    | P/D    |  4B    |  4B    | klen B  | vlen B  |
+--------+--------+--------+--------+---------+---------+
```

- `crc32` 覆盖范围：`op + klen + vlen + key + value`（即 crc 字段之后的全部字节）
- `op`：`'P'` = PUT（写/覆盖），`'D'` = DEL（删除）
- 全部小端序

### 为什么必须有 CRC

**崩溃时最后一条记录可能只写了一半**（torn write，撕裂写）。

比如进程正在写 `value` 字段的中途被 `kill -9`，文件里就留下一条"看起来格式正确、但内容不完整"的记录。恢复时如果盲目重放，就会把**垃圾数据**当成合法写入装进内存。

**CRC 就是用来识别这种情况的**：恢复时逐条校验，一旦失败就从这条开始截断。

### 实测证据

```
===== F. 撕裂写：截断文件中间 -> 恢复时识别并截断 =====
[WAL] 检测到 5 字节尾部损坏，已截断

===== G. CRC 损坏：翻转字节 -> 检出并丢弃 =====
[WAL] 检测到 450 字节尾部损坏，已截断
  (损坏点之前恢复了 25 条)
```

- **F**：砍掉文件最后 17 字节（必然落在某条记录中间）→ 恢复 97~99 条，尾部损坏被识别并截断
- **G**：翻转文件中部的 1 个字节 → 损坏点之后全部丢弃，之前的 25 条正常恢复

**注意 G 的行为是"丢弃损坏点之后的所有记录"，而不是"跳过这一条继续读"。**

为什么？因为一旦出现损坏，后面不可能再有可信的完整记录 —— 这是 WAL 的标准恢复语义（LevelDB、RocksDB 都这样）。

## 四、CRC32 实现

用标准 IEEE 802.3 多项式 `0xEDB88320`（和 zip/png/gzip 一致），查表法：

```cpp
uint32_t crc = 0xFFFFFFFFu;
for (size_t i = 0; i < len; i++)
    crc = table[(crc ^ p[i]) & 0xFF] ^ (crc >> 8);
return crc ^ 0xFFFFFFFFu;
```

**测试用标准向量验证**：

```cpp
CHECK(CRC32::compute("123456789") == 0xCBF43926u, ...);
```

`0xCBF43926` 是 CRC-32/ISO-HDLC 的标准测试值 —— **用公开测试向量验证，而不是自己和自己比**，这样才能证明实现是对的。

## 五、必须新增 `upsert_element`（补上缺陷 6）

### 问题

原版 `insert_element` 遇到已存在的 key **直接返回、不覆盖旧值**。所以 `SkipList` **没有 update 语义**，`Node::set_value()` 是死代码（架构文档里的缺陷 6）。

**WAL 重放必须要有覆盖语义**：

```
写入序列：  SET k v1 → SET k v2 → SET k v3
崩溃后重放：如果走 insert_element，只有 v1 生效，恢复结果错误
           必须走 upsert，才能得到 v3
```

### 实现

```cpp
int SkipList<K, V>::upsert_element(const K key, const V value) {
    std::unique_lock<std::shared_mutex> lock(_rwlock);
    // ... 找到每层前驱（和 insert_element 一样）
    if (current != NULL && current->get_key() == key) {
        current->set_value(value);      // ← 原地覆盖，终于用上了 set_value()
        return 1;                       // 1 = 更新
    }
    // ... 不存在则正常插入
    return 0;                           // 0 = 新插入
}
```

**为什么不写成"先 delete 再 insert"？**

- 那样会**重新掷硬币改变层高**，破坏索引结构
- 而且有短暂的"key 不存在"窗口，并发下别的线程可能读到中间态

**原地改 value 是最干净的做法。**

> 实测证据（测试 D 组）：
> ```
> db.put(7, "first"); db.put(7, "second"); db.put(7, "third");
> // 崩溃重启后
> CHECK(db.get(7, v) && v == "third", ...);   // ✅ 通过
> ```
> 如果重放走 `insert_element`，这里会得到 `"first"`。

## 六、快照与压缩

WAL 会**无限增长**：同一个 key 被改 100 次就有 100 条记录。

所以需要定期做**全量快照 + 清空 WAL**，把日志长度收敛到 O(数据量)。

### 顺序很重要

```
1. 先写快照到临时文件 .tmp
2. fsync + 原子 rename 成正式文件
3. 快照确认落盘后，才清空 WAL
```

**为什么不能反过来？**

如果先清 WAL 再写快照，中间崩溃 → WAL 没了、快照没写成 → **数据全丢**。

**用 `.tmp` + `rename` 的原因**：`rename` 在同一文件系统内是**原子操作**，要么看到旧快照，要么看到新快照，不会看到写了一半的文件。

### 实测效果

```
===== I. 快照后 WAL 被清空 =====
  (WAL 从 16890 字节压缩到 0 字节，快照 5890 字节)
```

**16890 → 0 字节**，WAL 被完全压缩。

### 快照 + WAL 组合恢复

```
===== H. 快照 + WAL 组合恢复 =====
CHECK(n == 152, "应恢复 100(快照) + 52(WAL) = 152 条记录");
CHECK(db.get(0, v) && v == "updated0", "快照中的 key 应被 WAL 覆盖为 updated0");
CHECK(db.get(50, v) && v == "old50", "快照中的 key=50 应保持 old50");
```

**关键验证**：快照里是 `key=0 → old0`，之后 WAL 里写了 `key=0 → updated0`。恢复后必须是 `updated0` —— **证明 WAL 能正确覆盖快照**。

## 七、kill -9 崩溃恢复演示（**最有杀伤力的部分**）

```bash
cd ~/Skiplist-CPP/fixed && make crash
```

### 演示设计

1. 写入进程持续写入，**每成功一条就把 key 打到 stderr**（用 `write()` 系统调用，无缓冲）
2. 脚本随机时刻 `kill -9`（**不可捕获、不可清理**，最粗暴的崩溃）
3. 启动恢复进程，**逐条校验所有 ACK 过的 key**是否都在、值是否正确
4. 重复多轮，每轮崩溃后重启继续写（模拟真实服务反复重启）

### 实测结果

```
---------------- 第 1 轮 ----------------
  在 0.81s 处 kill -9 (pid=78220)
  本轮 ACK 了 4096 条，最后一条 key=4095
  WAL 文件大小: 108399 字节
  RECOVER_RESULT recovered_records=4097 size=4097 checked=4096 missing=0 wrong=0
  ✅ 所有已确认的写入全部恢复（durability 成立）

---------------- 第 2 轮 ----------------
  在 0.81s 处 kill -9 (pid=78232)
  本轮 ACK 了 4116 条，最后一条 key=4115
  WAL 文件大小: 217311 字节
  RECOVER_RESULT recovered_records=8213 size=4116 checked=4116 missing=0 wrong=0
  ✅ 所有已确认的写入全部恢复（durability 成立）

---------------- 第 3 轮 ----------------
  在 0.38s 处 kill -9 (pid=78244)
  本轮 ACK 了 1991 条，最后一条 key=1990
  WAL 文件大小: 268875 字节
  RECOVER_RESULT recovered_records=10205 size=4116 checked=1991 missing=0 wrong=0
  ✅ 所有已确认的写入全部恢复（durability 成立）
```

**三轮 `kill -9`，每轮 `missing=0 wrong=0`。**

第 2 轮特别值得注意：`recovered_records=8213`（重放了全部 8213 条 WAL 记录），但 `size=4116`（去重后只有 4116 个不同 key）。**因为第 1 轮已恢复的 4097 条又被重放了一遍** —— 这正好验证了 `upsert` 的幂等性：**重复重放不会产生重复数据**。

## 十、诚实的局限

**1. fsync 没有真正调用**

标准 C++ 没有 `fsync` 接口。我用的是 `fstream::flush()`，它把数据交给**内核页缓存**，但没有强制刷到磁盘介质。

**这意味着**：
- `kill -9` 杀进程 → **数据不丢**（页缓存还在，测试证明了这点）✅
- **机器断电 / 内核 panic** → 页缓存里的数据会丢 ❌

要真正抗断电，需要 POSIX `fsync(fileno(f))`。我在代码注释里写明了这个边界。

**面试时主动说明**比被问出来好 —— 而且说明你理解"进程崩溃"和"机器断电"是两个不同级别的一致性保证。

**2. 每条写入都 fsync，性能很差**

没有做**组提交**（group commit）—— 工业实现会把多个并发写请求的 fsync 合并成一次。

**3. key 类型硬编码为 int**

`encode_key()` 用 `std::to_string(key)`，要支持 string key 需要抽象成 Codec（这是 P2 的内容）。

**4. 没有 WAL 自动触发快照**

`_wal_threshold` 定义了但没实现自动触发，需要手动调 `snapshot()`。

**5. 快照是全量重写**

没有做增量快照 / SSTable 分层，大数据量下快照会很慢（这是 P7 的内容）。

## 十一、面试话术

> "原版的持久化只有 `dump_file()`，需要手动调用、全量覆盖，而且**没有任何崩溃恢复能力** —— 进程被 kill，上次 dump 之后的所有写入全丢。
>
> 我加了 WAL 预写日志。核心是**先写日志并落盘，再改内存，最后才向调用方确认**。记录格式是 `crc32 + op + klen + vlen + key + value`，CRC 用来识别崩溃时的撕裂写。
>
> **恢复策略**是逐条重放，一旦 CRC 校验失败就从这条开始截断 —— 因为崩溃后不可能再有完整记录。
>
> 为了支持重放，我还得给跳表加 `upsert` 覆盖语义。原版的 `insert_element` 遇到重复 key 直接返回不覆盖，`set_value()` 是死代码。如果重放走原版逻辑，同一 key 写三次只会恢复第一次的值。
>
> **验证上我做了两组实验**：
> 一是 38 项单元测试，覆盖撕裂写、CRC 损坏、快照+WAL 组合恢复；
> 二是 `kill -9` 实测 —— 写入进程持续 ACK，脚本随机时刻强杀，恢复后逐条校验。**三轮全部 missing=0 wrong=0**。
>
> 我还做了对照实验：同样场景下，**原版恢复 0 条，WAL 版恢复 5000 条**。
>
> 另外我实现了快照压缩，WAL 从 16890 字节压缩到 0。快照用 `.tmp` + 原子 `rename`，保证不会看到写了一半的文件。
>
> **我也清楚一个局限**：我用的是 `flush()` 不是真正的 `fsync()`，所以能抗 `kill -9` 但**抗不了机器断电**。要真正持久需要 POSIX `fsync`，或者做组提交优化性能。"
