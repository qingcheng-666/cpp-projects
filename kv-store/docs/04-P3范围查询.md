# P3：迭代器 + 范围查询

> 代码：`fixed/skiplist.h`（搜索 `[P3]` 标记）
> 测试：`fixed/tests/p3_scan_test.cpp`（33 项断言）
> 基准：`fixed/tests/p3_bench.cpp`
> 一键运行：`cd fixed && make p3` / `make bench`

---

## 一、为什么 P3 比 P2 更值得先做

原版只有一个 `display_list()` 能**打印**整个跳表，没有任何**按范围取数据**的能力。

这是最可惜的地方，因为：

> **跳表相对哈希表唯一不可替代的优势，就是「有序 + 范围查询」。**

- Redis 的 **ZSET** 用跳表，是为了 `ZRANGE`（按分数范围取成员）
- LevelDB / RocksDB 的 **MemTable** 用跳表，是为了能**有序地刷盘**成 SSTable
- 如果只需要点查（`GET`/`SET`），哈希表 O(1) 更快，根本不需要跳表

**原版把跳表最大的卖点浪费了。** 补上 `scan()` 之后，你才能理直气壮地说："哈希表做不到的事，我能做。"

---

## 二、新增 API 一览

| API | 语义 | 复杂度 | 加锁 |
|---|---|---|---|
| `begin()` / `end()` | 迭代器，按 key 升序遍历 | O(1) 起 | ❌ 不加锁 |
| `lower_bound(k)` | 第一个 key >= k 的节点 | O(log n) | ❌ 不加锁 |
| `scan(a, b)` | 取 `[a, b)` 全部键值 | O(log n + k) | ✅ shared_lock |
| `scan_n(a, n)` | 从 a 起取 n 条 | O(log n + n) | ✅ shared_lock |
| `scan_reverse(k, n)` | <= k 的最大 n 条，降序 | O(range) | ✅ shared_lock |
| `count_range(a, b)` | 数区间内元素个数 | O(log n + k) | ✅ shared_lock |
| `seek(k, &ok, &ov)` | 第一个 >= k 的键值 | O(log n) | ✅ shared_lock |

## 三、核心实现：`lower_bound`

所有范围查询都建立在这一个函数上：

```cpp
Node<K, V>* lower_bound(const K& target) const {
    Node<K, V>* cur = _header;
    for (int i = _skip_list_level; i >= 0; i--) {
        while (cur->forward[i] != nullptr && cur->forward[i]->get_key() < target) {
            cur = cur->forward[i];
        }
    }
    return cur->forward[0];       // 第一个 key >= target 的节点
}
```

**这段代码和 `search_element` 的前半部分几乎一样**，唯一区别是：

- `search_element` 最后判断 `current->get_key() == key`（**等于**才命中）
- `lower_bound` 直接返回 `cur->forward[0]`（**大于等于**就返回）

**为什么这个区别很重要？**

因为它把"点查"变成了"区间起点"。一旦定位到区间起点，**后续就是沿 level 0 顺序扫**，不需要再走索引：

```
scan(30, 50) 的过程：

  L3 │ H ──────────────────────────> 100
  L2 │ H ──────> 30 ───────────────> 100
  L1 │ H ──> 10 ──> 30 ──> 50 ─────> 100
  L0 │ H ──> 10 ──> 30 ──> 50 ──> 70 ──> 100
                    ↑
              ① O(log n) 定位到这里
                    └──── ② 沿 L0 顺序扫到 50 之前 ────┘
```

**总复杂度 O(log n + k)**，k 是区间内元素个数。

而哈希表因为**无序**，想按 key 范围取数**只能全量扫一遍**（O(n)）。

## 四、并发安全：这是 P3 最需要想清楚的设计

### 问题

迭代器持有的是**裸 `Node*`**。一旦有并发写：

- `insert` 会改 `forward` 指针 → 迭代器可能跳到错误的节点
- `delete` 会 **`delete` 掉节点** → 迭代器直接**悬空**，解引用就是野指针 → 崩溃

**这是所有 KV 引擎都要面对的问题**，业界有几种做法：

| 方案 | 代表 | 代价 |
|---|---|---|
| 单线程，根本不并发 | Redis（核心命令单线程） | 无法利用多核 |
| 迭代器 + 引用计数 / 版本号 | LevelDB | 实现复杂 |
| 迭代期间加锁，不许写 | 简单实现 | 长时间阻塞写 |
| **快照：加锁拷贝后立刻释放** ✅ | 我用的这个 | 拷贝开销 |

### 我的设计：两套 API，调用方按场景选

```cpp
// (1) Iterator —— 轻量、零拷贝，但【不加锁、不安全】
//     要求：调用方保证遍历期间没有并发写
for (auto it = sl.begin(); it != sl.end(); ++it) { ... }

// (2) scan() 系列 —— 内部加 shared_lock，拷进 vector 后立即释放锁
//     返回的是【快照】，多线程安全
auto rows = sl.scan(100, 200);
```

**为什么这么分？**

- 单线程场景（比如 `main.cpp` 的 demo）：用迭代器，**零开销**
- 多线程场景（比如 P6 的网络服务）：用 `scan()`，**安全**，代价是一次拷贝

**这个取舍我在代码注释和文档里都写明了** —— 面试时主动说清楚"我知道这里有悬空风险，所以提供了两种 API"，比被面试官问出来强得多。

### `mutable` 那个坑

`scan()` 是 `const` 成员函数，但加锁会改锁的内部状态。`const` 函数里 `_rwlock` 是 `const` 的，而 `shared_lock` 需要**非 const 引用**，编译报错：

```
error: no matching function for call to
'std::shared_lock<std::shared_mutex>::shared_lock(const std::shared_mutex&)'
```

**修法**：把锁声明为 `mutable`：

```cpp
mutable std::shared_mutex _rwlock;
```

**这是标准做法**：锁是"逻辑上不改变对象状态"的同步设施，所以 `mutable` 是合理的。

> 这个坑很典型，**面试时能说出来说明你真写过并发代码**。

### 另一个坑：迭代器解引用的悬空引用

原版的 `get_key()` / `get_value()` 是**按值返回**的：

```cpp
K get_key() const { return key; }        // 返回临时对象
```

如果迭代器这样写：

```cpp
struct ArrowProxy {
    const K& first;      // ← 绑定到临时对象！
    const V& second;
};
ArrowProxy operator->() const {
    return ArrowProxy{_node->get_key(), _node->get_value()};   // 临时对象语句结束即销毁
}
```

**`it->first` 会立刻变成悬空引用**，读到垃圾值。

**修法**：给 `Node` 加引用版访问器：

```cpp
const K& get_key_ref() const { return key; }
const V& get_value_ref() const { return value; }
```

迭代器用 `_ref` 版本。**这个问题只有真写出来跑才会发现**，光看代码很容易忽略。

## 六、性能基准（100 万条数据）

```bash
cd ~/Skiplist-CPP/fixed && make bench
```

每次取 100 条，重复 1000 次：

| 方式 | 总耗时 | 单次 | 相对倍数 |
|---|---|---|---|
| **1. 跳表 `scan()`** | 25.77 ms | 25.8 µs | **1.00x** |
| 2. `std::map` `lower_bound` | 25.87 ms | 25.9 µs | 1.00x |
| 3. 哈希表全量扫描 | 108045 ms | 108 ms | **4193x** |

### 怎么解读这个结果

**跳表和 `std::map` 打平（1.00x）** —— 这是**符合预期**的，因为两者都是 O(log n) 定位。跳表的优势不是"比红黑树快"，而是"**实现简单 + 并发友好 + 无旋转**"。

**哈希表慢 4193 倍** —— 这才是重点。哈希表无序，范围查询只能全量扫 100 万个元素。

> **这个 4193 倍就是"跳表为什么存在"的答案。**

### 面试怎么说这组数据

> "我做了范围查询的基准测试，100 万条数据下取 100 条：
> 跳表 `scan()` 单次 25.8 微秒，和 `std::map` 的 `lower_bound` 打平——因为都是 O(log n) 定位。
> 但同样的操作，哈希表因为无序只能全量扫描，要 108 毫秒，**慢了 4000 多倍**。
> 这就是 Redis ZSET 和 LevelDB MemTable 都选跳表的根本原因。"

**有数字、有对比、有结论** —— 这是面试里最有杀伤力的表达方式。

## 七、一个诚实的局限：`scan_reverse` 不是 O(log n)

原版跳表**只有 `forward` 指针，没有 `backward`**。所以反向遍历**做不到** O(log n + k)。

我的 `scan_reverse` 实现是：

```cpp
// 先从头正向扫到 start_key，收集全部，再从末尾截取 n 条，最后反转
for (Node<K,V>* p = _header->forward[0]; p && p->get_key() <= start_key; p = p->forward[0])
    out.emplace_back(...);
if (out.size() > n) out.erase(out.begin(), out.end() - n);
std::reverse(out.begin(), out.end());
```

**复杂度是 O(range) 而不是 O(log n + n)。**

### 工业界怎么解决

**给 level 0 加双向链表**（每个节点多一个 `backward` 指针）。Redis 的跳表就是这么做的：

```c
typedef struct zskiplistNode {
    ...
    struct zskiplistNode *backward;    // ← Redis 有这个
    struct zskiplistLevel { ... } level[];
} zskiplistNode;
```

这样 `ZREVRANGE` 才能高效实现。

**我在文档里把这一点写清楚了** —— 面试时**主动说明**"我的反向遍历是简化版，真正的工业实现会加 backward 指针"，比被问出来好得多。

**这是 P4/P5 可以做的优化点。**
