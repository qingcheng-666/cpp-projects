## 1. 整体定位

一个**纯内存 + 可选落盘**的轻量 KV 存储引擎，核心数据结构是**跳表（Skip List）**。
它没有任何网络层、没有服务端、没有命令行客户端——本质是一个**可 `#include` 的 C++ 头文件库**（header-only 的雏形），
`main.cpp` 只是一个演示 `skiplist.h` 怎么用的 demo。

对比你之前的恋恋风辰聊天室（网络 + 业务 + 数据库 + 线程池），这个项目的价值**完全不同**：
它不考工程组织，只考**一个数据结构 + 并发 + 持久化**这三件事讲得够不够深。这正是面试官爱问的点。

```
                     ┌──────────────────────────────┐
                     │  main.cpp（demo，~40 行）      │
                     │  insert / search / display /  │
                     │  delete / dump_file           │
                     └───────────────┬──────────────┘
                                     │ #include "skiplist.h"
                     ┌───────────────▼──────────────┐
                     │  skiplist.h（核心，~400 行）   │
                     │                              │
                     │  ┌────────────────────────┐  │
                     │  │ SkipList<K, V>         │  │
                     │  │  _header ──┐           │  │
                     │  │  _max_level│           │  │
                     │  │  _skip_list_level      │  │
                     │  │  _element_count        │  │
                     │  │  _file_writer/reader   │  │

                     │  │  key / value           │  │

                     ┌───────────────▼──────────────┐

                     └──────────────────────────────┘
```

## 2. 数据结构设计

### 2.1 Node —— 每个节点自带"层高"

```cpp
template<typename K, typename V>
class Node {
public:
    Node<K, V> **forward;   // 指针数组，长度 = level + 1
    int node_level;         // 本节点层高
private:
    K key;
    V value;
};
```

- `forward` 是**变长指针数组**（`new Node*[level+1]`），下标 `i` 指向"本节点在第 i 层的后继"。
- 层数由插入时随机决定，所以不同节点的 `forward` 长度不同。
- 注意：`forward` 和 `node_level` 是 `public`，`key/value` 是 `private`，只能通过 `get_key()/get_value()/set_value()` 访问。

### 2.2 SkipList —— 持有 header 和状态

```cpp
Node<K, V> *_header;        // 头节点，层高固定为 _max_level（不存业务数据）
int _max_level;             // 允许的最大层数（main 用 6，压测用 18）
int _skip_list_level;       // 当前实际最高层（动态收缩）
int _element_count;         // 元素个数
std::ofstream _file_writer; // 落盘用
std::ifstream _file_reader; // 加载用
```

`_header->forward[i]` 是第 `i` 层的**链表头**，本身不存 key。

### 2.3 层高随机策略（面试高频）

```cpp
int get_random_level() {
    int k = 1;
    while (rand() % 2) { k++; }                 // 每次 1/2 概率继续升层
    k = (k < _max_level) ? k : _max_level;      // 封顶
    return k;
}
```

- 几何分布：`P(level = 1) = 1/2`，`P(level = 2) = 1/4`，`P(level >= k) = 2^-(k-1)`
- 期望层高 ≈ **2**（级数 `1 + 1/2 + 1/4 + ... = 2`）
- 所以 100 万节点大约只有 1~2 个节点能到 18 层 —— 这正是跳表"用空间换时间"的代价极低的原因。
- **层高从 1 起步**（不是 0），意味着每个节点至少占 2 个 forward 槽，level 0 和 level 1 永远被填满。略微浪费，但实现简单。

## 3. 核心算法

### 3.1 查找（O(log n) 期望）

从最高层 `_skip_list_level` 出发，在每层向右走到不能再走，再下一层：

```cpp
for (int i = _skip_list_level; i >= 0; i--)
    while (current->forward[i] && current->forward[i]->get_key() < key)
        current = current->forward[i];
current = current->forward[0];   // 落到 level 0 的候选节点
```

### 3.2 插入

与查找同路径，但**额外记录每层的前驱**到 `update[]`，然后：

```cpp
Node<K,V>* update[_max_level + 1];   // 注意：这是 VLA（C 扩展），非标准 C++
// ... 查找到达 level 0，途中 update[i] = current
int random_level = get_random_level();
if (random_level > _skip_list_level) {
    for (int i = _skip_list_level + 1; i <= random_level; i++) update[i] = _header;
    _skip_list_level = random_level;          // 抬高当前最高层
}
Node<K,V>* node = create_node(key, value, random_level);
for (int i = 0; i <= random_level; i++) {     // 逐层插入，等价于链表头插
    node->forward[i] = update[i]->forward[i];
    update[i]->forward[i] = node;
}
```

**语义细节（容易被面试官追问）**：
- key 已存在时**直接返回 1，不覆盖旧 value**。也就是说 `SkipList` **没有 update 语义**，`Node::set_value()` 实际上从未被调用过 —— 想改值只能先 `delete_element` 再 `insert_element`。
- 返回值：`1` = key 已存在，`0` = 插入成功。

### 3.3 删除

同样先求 `update[]`，然后逐层摘链，并在最后**收缩** `_skip_list_level`：

```cpp
for (int i = 0; i <= _skip_list_level; i++) {
    if (update[i]->forward[i] != current) break;   // 该层没有这个节点，跳出
    update[i]->forward[i] = current->forward[i];
}
while (_skip_list_level > 0 && _header->forward[_skip_list_level] == 0)
    _skip_list_level--;                            // 高层空了就降下来
delete current;
```

### 3.4 析构（有坑，见第 6 节）

```cpp
if (_header->forward[0] != nullptr) clear(_header->forward[0]);  // 递归！
void clear(Node<K,V>* cur) {
    if (cur->forward[0] != nullptr) clear(cur->forward[0]);      // 沿 level 0 递归到底
    delete cur;
}
```

递归深度 = **节点总数**，不是层数。

## 4. 持久化设计

| 接口 | 行为 |
|---|---|
| `dump_file()` | 沿 level 0 遍历，按 `key:value\n` 覆盖写入 `store/dumpFile` |
| `load_file()` | 逐行读，用 `:` 切分，`stoi(key)` 转 int 后 `insert_element` |

**格式与硬编码**：
- 路径来自宏 `#define STORE_FILE "store/dumpFile"` —— **相对路径**，实际落点取决于进程 CWD。
- `load_file()` 里写死了 `stoi(*key)`，所以**key 必须是 int**；想换成 string key 必须改这里（README 的"待优化"也承认了）。
- value 取 `:` 之后的全部内容（`substr(find+1)`），所以 **value 里可以含 `:`，但 key 里不能**。
- 仓库里自带的 `store/dumpFile` 内容是 `1:a;`（**带分号**），而 `dump_file()` 写出的是 `1:a`（**不带分号**）—— 两者格式不一致，是历史遗留。若你直接 `load_file()`，value 会带上多余的 `;`。
- 这**不是 WAL**：每次 dump 都是全量覆盖，没有增量、没有 fsync、没有崩溃恢复。

## 5. 并发模型（这是最大的面试风险点）

```cpp
std::mutex mtx;      // 全局变量！定义在头文件里
std::string delimiter = ":";   // 同样是头文件里的全局定义
```

- **一把全局锁**，且定义在头文件中 → 所有 `SkipList` 实例、所有翻译单元共享同一把锁。
- 只有 `insert_element` 和 `delete_element` 加锁。
- **`search_element` / `display_list` / `dump_file` / `load_file` / `size` 全都不加锁。**
- `get_random_level()` 内部调用 `rand()`，而 `rand()` 本身**不是线程安全的**，且在锁内被调用 —— 但 `search` 不加锁，无法构成读写互斥。

结论：**这个"线程安全"是假的**。它是一个"写写互斥"的容器，不是"读写安全"的容器。实测证据见第 6 节。

## 6. 实测验证的缺陷（我在你的 VM 上真实跑出来的）

> 环境：Ubuntu 22.04.5，g++ 11.4.0，内核 6.8。

### 缺陷 1 —— 递归析构会爆栈（**严重**）

```cpp
// 100 万节点，正常析构
delete sl;
```
```
inserted 1000000 nodes, size=1000000
destroying recursively...
B exit=139          ← 段错误（核心已转储）
```

**原因**：`clear()` 沿 level-0 链递归，深度 = 节点数 = 100 万。默认栈 8MB，每帧约 48 字节 → 需要约 48MB，直接爆栈。
**修复**：改成迭代，沿 `forward[0]` 逐个摘链删除；或维护 `std::vector<Node*>` 辅助。

### 缺陷 2 —— 头文件里定义全局变量，多翻译单元链接冲突（**严重**）

两个 `.cpp` 同时 `#include "skiplist.h"` 后链接：
```
/usr/bin/ld: multiple definition of `mtx'; first defined here
/usr/bin/ld: multiple definition of `delimiter[abi:cxx11]'; first defined here
collect2: error: ld returned 1 exit status
```

**原因**：`std::mutex mtx;` 和 `std::string delimiter = ":";` 是**定义**而非声明，被每个 TU 重复定义。
**影响**：这直接堵死了"多文件工程化"—— 你一旦想把它拆成 `kv_server.cpp` + `main.cpp` 就编不过。
**修复**：C++17 用 `inline`；或把定义移入 `.cpp`，头文件只留 `extern`；或包进匿名 namespace/`static`（但那样每个 TU 一把锁，语义又不对）。

### 缺陷 3 —— `search_element` 无锁，与写并发时是数据竞争（**严重**）

用 ThreadSanitizer 实测（写线程 insert + 读线程 search）：
```
WARNING: ThreadSanitizer: data race
  Read of size 4 at ... by thread T2:
    #0 SkipList<int, std::string>::search_element(int)
  Read of size 8 at ... by thread T2:
    #0 SkipList<int, std::string>::search_element(int)
```
**后果**：并发读写时 `search` 可能读到正在被改写的 `forward` 指针，轻则查错、重则**解引用野指针崩溃**。
**修复**：`std::shared_mutex`（读共享 / 写独占），`search` 加 `shared_lock`，`insert/delete` 加 `unique_lock`。

### 缺陷 4 —— `dump_file()` 失败时静默丢数据

`store/` 目录不存在时执行 `dump_file()`：
```
dump_file() returned normally, exit code will be 0
ls: 无法访问 'store': 没有那个文件或目录
```
**原因**：`_file_writer.open(STORE_FILE)` 之后**从不检查 `is_open()`**，照样打印成功、返回 `void`、进程退出码 0。
**后果**：数据看起来"落盘成功"，实际一条都没写。生产环境的静默数据丢失。
**修复**：`if (!_file_writer.is_open()) return false;`，接口改为返回 `bool`，并向上层暴露错误。

### 缺陷 5 —— README 的 QPS 数字在本机复现不了

README 宣称 **写 24.39w QPS / 读 18.41w QPS**。我在你 VM 上用同样 10 万条随机插入实测：

| 版本 | 10 万条插入耗时 | QPS |
|---|---|---|
| **原样代码**（每次 insert 都 `std::endl` 刷缓冲 + 打印） | 12.90 s | **7,753** |
| 仅把 `std::endl` 换成 `"\n"` | 5.33 s | 18,765 |
| 完全去掉插入路径的打印 | 5.12 s | **19,517** |

**结论**：
1. 原样代码的性能**被日志打印彻底支配** —— 单次 `endl` 的 flush 系统调用让 QPS 掉了 **2.5 倍**。
2. 即使把打印全部去掉，本机也只有约 **1.95w QPS**，比 README 宣称的 24.39w **低约 12 倍**。
3. 所以面试时**不要引用 24.39w 这个数字**，否则被追问"你测过吗、怎么测的"会很难看。自己重测一遍、讲清楚测试条件（单线程 / 随机 key / 是否含 IO）才是加分项。

### 其他值得知道的小问题

| 问题 | 说明 |
|---|---|
| `Node<K,V>* update[_max_level+1]` | VLA，GCC 扩展，MSVC 不支持；`_max_level` 大时栈开销大 |
| `_element_count` 是 `int` | 超过 21 亿条溢出；且 `size()` 不加锁 |
| `rand()` 非线程安全 | `get_random_level()` 并发调用时竞争 |
| 无 update 语义 | 重复 key 不更新 value，`set_value()` 是死代码 |
| 无迭代器 | 只能 `display_list()` 打印，无法按范围遍历 —— 而范围查询正是跳表相对哈希表的卖点 |
| 无 TTL / 无内存上限 | 纯内存，无淘汰策略 |

## 7. 复杂度总结（背下来）

| 操作 | 期望 | 最坏 |
|---|---|---|
| 查找 | O(log n) | O(n) |
| 插入 | O(log n) | O(n) |
| 删除 | O(log n) | O(n) |
| 空间 | O(n)（期望每节点 2 个指针） | O(n log n) |

跳表 vs 红黑树 vs 哈希表（面试必答）：
- **vs 红黑树**：跳表实现简单、无需旋转、**天然支持范围查询**、并发下锁粒度更好做（可以只锁局部）；代价是常数更大、最坏情况概率性 O(n)。
- **vs 哈希表**：哈希表查询 O(1) 更快，但**不支持有序遍历/范围查询**，且扩容代价大。Redis 的 ZSET 就是跳表（有序）+ 哈希表（O(1) 查分值）的组合。
- Redis / LevelDB / RocksDB 的 MemTable 都选了跳表，核心原因就是**范围查询 + 并发友好 + 实现简单**。

## 8. 面试怎么讲这个项目（建议话术）

不要平铺直叙"我实现了跳表"。按这个顺序讲，每个点都留了钩子给面试官：

1. **数据结构选型**：为什么 KV 引擎用跳表而不是红黑树/哈希表 → 范围查询 + 并发友好 + 实现简单，Redis ZSET 同款。
2. **核心算法**：插入时维护 `update[]` 前驱数组，一次查找完成多层插入；随机层高几何分布，期望层高 2，空间代价极小。
3. **主动暴露并修复缺陷**（**这是最强的加分项**）：
   - "原版析构是递归的，我实测 100 万节点会爆栈，改成了迭代析构。"
   - "原版把 `mtx` 定义在头文件里，多文件工程链接会 multiple definition，我用 C++17 `inline` 修掉了。"
   - "原版 `search` 不加锁，我用 TSan 跑出了数据竞争，换成了 `shared_mutex` 读写锁。"
   - "原版 `dump_file` 不检查 `is_open()`，磁盘/目录异常时会静默丢数据。"
   - "README 说 24 万 QPS，我实测去掉打印只有约 2 万，因为原版每次插入都 `endl` 刷盘。"
4. **你的扩展**（见 `02-魔改路线图.md`）：加上网络层 → 变成真正的 KV 服务；加上 WAL + SSTable → 就是迷你 LevelDB。
